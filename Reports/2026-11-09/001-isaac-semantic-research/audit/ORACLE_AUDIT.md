# DREAM oracle and hardcoding audit (object search and original-goal work)

Branch `claude/isaac-semantic-research-20261109`. Read-only audit by code inspection; nothing was run and nothing in the repository was changed. Line numbers are from this checkout. Statements marked HYPOTHESIS are inferences, not things I verified by running.

## 1. Direct answer

No decision-side code contains a fixed object location, a room layout, a route, a seed or config-name branch, or a target-specific success rule. The planner, the belief, the verifier and the toolbox only ever touch the robot's own frames, its odometry and the ConceptNet extract. The tests enforce the import side of that, and I found no code path that bypasses it (section 3, item 7). The real problem is not hidden answer-passing. It is that the benchmark is built from the author's own assumptions at both ends, and several of them are friendlier to the agent than a real robot would get:

- **Oracle perception (MuJoCo).** The detector is the true instance segmentation, with exact per-object masks, the true class label with 80-95% probability per frame, and independent errors per frame (`dream/sim/semantic_sensor.py:132-152`). Independent errors are what make multi-view voting almost perfect.
- **Oracle odometry.** True increments plus 2% noise, in MuJoCo and in Isaac.
- **Shared author assumptions.** The same author wrote the furnishing tables, the confusion groups, the agent's assumed sensor model and the scoring.
- **Closed vocabulary.** The agent's object list equals the generator's class list, and the ConceptNet extract was queried for that same list.
- **Frozen seeds.** All thresholds and the verifier rule were fixed or revised after seeing the H1-H4 and H2 outcomes.

So the claim "the robot knows nothing about the answers" holds. The claim that results transfer to a real robot with a real detector does not follow, and the README already says so in most places. The numbers most likely inflated are the verifier's false-claim rate (0/192 in V1, 0/480 gates), search speed and success under H1-H3, and the room-inference accuracy. The Isaac results say little about search ability: the one present-target search task (the sink) was missed in the only kitchen it ran, and the 0/9 false-success result is mostly "the system refused" on absent or unsupported targets.

## 3. Per-item notes

**1-3. Locations, layouts, routes.** I searched `dream/runtime`, `dream/tools`, `dream/semantics`, `dream/perception`, `dream/navigation`, `dream/memory`, `dream/agent` and `dream/skills` for object names, room names and coordinates. Object and room names appear only in docstrings and in `ROOM_CATEGORIES` (`knowledge.py:35-38`, a vocabulary, not a layout). `semantic_search.py:38` states the same claim, and the code is consistent with it. The planner picks viewpoints from the occupancy grid, the belief mass and the tracks (`semantic_search.py:261-330`). Nothing in it reads a generator field.

**4. Target identity.** `semantic_search_eval.py:149-153` builds the grammar vocabulary as `homes.CLASSES + ["kettle"]` and `semantic_search_eval.py:~257` passes `object_classes=frozenset(homes.CLASSES)` to `Capabilities`. The sensor's false-positive vocabulary is the same list (`semantic_sensor.py:~75`, `vocabulary=CLASSES`). So the agent can only be asked for, and can only hallucinate, benchmark classes. In Isaac the equivalent list is `DETECTOR_VOCABULARY` (`experiments/isaac_semantic.py:43-48`): 14 names that were written to match the task statement (its comment says so). Six exist in the kitchens, and the rest are distractors and absent targets ("bed", "kettle", "refrigerator"). That is a closed-set detector with the answer set listed in the prompt, not an open-vocabulary one.

4a. The request text itself comes from the generator (`home.py:1394`, `f"Find the {name}"`) and from the config for Isaac. That is just the user's request and is legitimate input.

**5. Success conditions.** `verify_find` (`dream/semantics/verify.py:112-163`) and `TaskAgent` work from tracks and pose only. Nothing in the verifier knows a scene. `REQUIRED_CLASSES = ("sink",)` makes the Isaac process refuse to run without a sink in scene truth (`isaac_semantic.py:69`, `isaac_g1_live.py:299-302`), which is a scorer precondition, not an agent rule.

**6. Qwen prompts, all of them.**
- Detector (`dream/perception/vlm_detect.py:27-32`): "List every object of these classes that is visible in the image: {classes}..." plus the image. The class list is the full 14-name vocabulary, not only the requested target. No target location, room, or scene name. No leak beyond the closed vocabulary.
- Grounding system prompt (`dream/runtime/mobile_model.py:~475-483`) and message (`:~468-474`): the request, the object vocabulary with synonyms, the room vocabulary, remembered place names and the outcome list. Used only if the grammar leaves target or outcome ungrounded. Result is checked against the request's own words (`check_anchoring`). The prompt warns against substituting the target, which is a behavioural instruction learned from the 7 Nov failure, not a scene answer.
- Goal interpretation (`mobile_model.py:~157-189`) and tool selection (`:~332-343`), used by the 7 Nov arm and by Inspect: the instruction text lists capabilities and the admissible actions. The admissible-action list is computed from the robot's observation (`available_actions`, `:247-281`), so the model chooses among a short menu that code has already restricted to valid viewpoints, candidates and frontiers. That helps the model: it cannot produce an invalid action, and a `finish` is only accepted when `verdict.satisfied` (`:~365-380`).
- Room-prior elicitation (`experiments/qwen_room_priors.py:30-40`): "For the household object {obj}, how likely is it to be found in each type of room?" No scene or benchmark content. `main` iterates `knowledge["objects"]`, which are the benchmark-aligned names. Output is explicitly not used by any agent.
- I found no prompt that contains an evaluation answer, a scene description, a coordinate, a seed or a scoring rule.

**7. Ground-truth leakage and what the isolation test guards.**
- What reaches the agent: the toolbox is built as `MobileToolbox(meter, ...)` where `meter` is a `PathMeter` wrapping the base (`semantic_search_eval.py:117-146,~305`). The toolbox calls only `capture`, `odometry`, `walk`, `time`, `stop_reason` (my grep of `base\.` over all decision packages: those five plus an unrelated `base.position/size` in `goals.py:216-218` that belongs to a candidate object, plus one `getattr(self.base, "controller", None)` in `tools/mobile.py:643` for the commanded velocity). No call to `true_pose`, `contact_log`, `home`, `model` or `data`.
- Where truth is reachable by object reference but not used: `PathMeter.__getattr__` forwards every unknown attribute to the inner base (`semantic_search_eval.py:124-125`). The inner base is a `KinematicBase` with `.home`, `.model`, `.data`, `.true_pose`, `.contact_log`, or a `SemanticG1Base` with `.base.env` and `.semantic`. So the model, data and HomeSpec are one attribute hop from the toolbox. Nothing uses them. This is a structural weakness: only convention and the tests prevent a future use.
- Frames: `RGBDFrame` carries depth, RGB, `self_mask`, calibration, `detections` (`kinematic_base.py:197-209`). The semantic sensor holds the MjModel and the geom-to-instance index (`semantic_sensor.py:91-110`) but returns only `SemanticDetection(label, score, mask, source)` (`:152`). Instance ids, geom ids and true distances are not returned.
- Calibration passed with each frame is the camera pose in the ODOMETRY frame (`kinematic_base.py:198-205`), not the world frame.
- What `tests/test_isolation.py` checks: for the packages `agent, skills, tools, runtime, perception, navigation, memory, semantics` it (a) parses every import and rejects `mujoco`, `dream.sim`, `dream.eval`, `dream.robot` (`:17,41-46`), (b) rejects any attribute or name containing `privileged`, `MechanismSpec`, `TabletopSpec`, `CompartmentSpec`, `_spec`, `HomeSpec`, `ObjectSpec`, `GroundTruthView` (`:18-21,49-56`), (c) checks that nothing imports `task_scoring` (`:69-75`), (d) checks the robot adapter. I found these gaps:
  - `from dream import sim` yields module `"dream"`, which does not start with `dream.sim`, so it passes the import check (`_imports` records only `node.module`, `:34-35`). Relative imports (`from ..sim import x`) are also not caught. `importlib` and `__import__` are not checked.
  - The name check does not include `true_pose`, `contact_log`, `model`, `data`, `home` or `memory_prior`, and does not look at string arguments, so `getattr(base, "true_pose")` passes. A string-based `getattr` already exists in `tools/mobile.py:643`, harmless but the same pattern.
  - `dream/types.py`, `dream/session.py`, and the whole `experiments/` directory are outside the guarded set. The experiments are where the wiring that builds the toolbox lives (`semantic_search_eval.py`, `isaac_g1_live.py`).
  - The check is static. It cannot see what is handed over at runtime (the `PathMeter` case above).
  - Conclusion: no bypass in use; the guard is weaker than the stated invariant.
- Callbacks and closures: `TaskAgent.run(..., on_event=shadow.on_event)` (`semantic_search_eval.py:332`) hands evaluation code a hook into the agent loop. It is read-only (item 18). `memory_hints` closes over `home` and runs before the agent starts (item 9). `capture_decision` in `isaac_g1_live.py` records data for logs, not decisions.
- Isaac: `labelled_objects(world.stage)`, `handle_truth`, `obstacle_boxes`, `true_instances` are built in the live process and are marked evaluation only (`isaac_g1_live.py:280-325`). **8. Scripted actions vs model reasoning.** In the MuJoCo benchmark there is no model at all (`model_calls: 0`, `semantic_search_eval.py:~375`), and the README says so ("no language model is in that loop"). In the Isaac semantic arm, for `FindObject` goals the actions come from `SemanticSearchPlanner`, a deterministic utility planner (`isaac_semantic.py:134-148`). Qwen supplies only detections (`VLMDetector`) and, if the grammar fails, a validated grounding. The config text says this (`isaac_semantic_eval.json`, "semantic" arm description), but its `process_rule` says "Each task is submitted through the real phone API with provider 'qwen'. No scripted controller" and `isaac_g1_live.py:~420` requires `task.meta["provider"] == "qwen"`. A reader could take that to mean Qwen chose the search actions. It did not for FindObject; it did for the old arm and for Inspect (where its choice is restricted to a menu, above). The Isaac "reasoning" strings are not presented as model reasoning in the code I read; I did not read the result files.

**9. Generator metadata.** Besides `memory_prior`, the agent receives nothing from the generator except the request string. Room labels, the furnishing tables and `TARGETS` (`home.py:316-343`) are used only to build scenes and, via `room_at`, to label `TrueInstance.room_type` for scoring (`semantic_search_eval.py:~262`).

**10. Seed- and config-specific logic.** None in agent code. Config values enter as constructor arguments (`VerifierThresholds(**cfg["verifier"])`, `UtilityWeights(**cfg["weights"])`), identical for every seed. Config names such as `dev3` or `H1` appear only in experiment configs. Comments in `perception/detect.py:312`, `perception/spatial.py:37,130`, `tools/mobile.py:67` mention development seeds (room seed 1, seed 1013, drawer seed 3) as the origin of constants; those belong to the older tabletop and room work, not to the search path.

**11. How much the MuJoCo semantic sensor reveals.** Per frame it renders geom-id segmentation at 320x240 from the head camera (robot geoms hidden), maps geoms to benchmark instances, and for each visible instance:
- Detects it with probability logistic((pixels - 250)/60), zero below 30 pixels (NOMINAL; DEGRADED uses 450/100). Detection is therefore tied to true visible size.
- Returns the true class, except with probability 0.05 (at 1.5 m) rising to 0.2 (at 3 m) it returns a uniformly chosen member of the class's confusion group (`semantic_sensor.py:134-148`).
- Returns the exact pixel mask of the whole instance, with perfect object boundaries and exact grouping of all parts of an object (a counter, sink and cabinet are separate objects). The Isaac Qwen boxes fuse them, README line 473 reports the resulting failure.
- Returns a score drawn from N(0.75, 0.12) for correct and N(0.6, 0.15) for confused labels, deliberately overlapping so scores carry little information.
- Adds 0.03 spurious detections per frame (0.08 degraded) on random scene chunks.
- Does not reveal instance ids, true distances or poses. Unseen or fully occluded objects are not reported, and objects beyond 3 m or without a depth return are not reported.
- Errors are drawn independently per frame and per instance from the sensor's own RNG. A real detector's errors are strongly correlated across nearby views of the same object (same lighting, same occluded part). HYPOTHESIS: independence is why multi-view voting plus the Wilson rule reach 0/192 false claims; with correlated errors that figure would be an optimistic bound. The README lists the verifier as confirmed "only with the nominal detector model", but does not name this correlation.

**12. Odometry.** Position increments are the true increments times (1 + N(0, 0.02)); yaw has 2% scale noise and a per-episode bias drawn from N(0, 0.002 rad/s) (`g1_mobile.py:87-96,175-192`; same model in the kinematic base and Isaac). The robot never has to localise or close loops. The scorer compensates for drift by comparing true pose and odometry at the end (`odometry_to_world`), so odometry drift is not charged to the agent either. HYPOTHESIS: for long searches the map would drift and doors would smear in a real robot, and none of the search arms is tested for that.

**13. Camera.** In the search benchmark the colour image is all zeros (`kinematic_base.py:107-110`, `rgb=False` in `semantic_search_eval.py:~212`), so nothing can use appearance. Depth is a clean mesh render with small Gaussian noise and 1 mm quantisation, NaN beyond 3 m (`kinematic_base.py:112-120`), and no holes, multipath or reflective failures. The README declares this as "speed change, not a task change". It is a task change for any method that wants colour, and a simplification of the depth sensor. Resolution and FOV match the G1 model (58 deg, 320x240) and the 3 m range is a genuine restriction that makes the task harder than a real RGB-D sensor would.

**14 (details). Agent sensor model vs simulated sensor.** `detection_quality` (`perception/semantic.py:40-50`: 0.85 to 2 m, falling to 0.4 at 3 m) feeds coverage, the belief mass, and the value of a look (`belief.py` `view`). `CLOSE_RANGE = 2.5` and `VERIFY_RING = (1.2, 2.0)` are described in comments as "the coverage model's good band". The simulated sensor has confusion rising with range between 1.5 m and 3 m and a 3 m hard limit. The two models are different functions, but the agent's assumption has the same range structure and was written by the same author. HYPOTHESIS: a real detector with different range behaviour would shift the optimal rings and thresholds; no experiment varies the agent's assumed model while keeping the true sensor fixed.

**18. Shadow acceptance logging.** `ShadowAcceptances` (`semantic_search_eval.py:231-290`) is called from `on_event` for `verification` and `result` events. It reads `world.map.candidates`, builds a *new* `VerifierThresholds` with `dataclasses.replace` (so the live thresholds are not mutated), calls `check_track` (pure function, no RNG), reads `true_pose()` and `base.odometry()` (both return copies) and writes only to its own dict. `PathMeter.walk` also reads `true_pose()` before and after (`:139-143`). It uses no RNG draw and mutates no agent state, so it cannot change an agent decision. One limit: `world.refresh()` is called after the episode in `_run` (`:~348`) and mutates `world` after the verdict is read, which only affects the room scoring that follows.

**claim_nearest.** It is created only in `score_episode` (`dream/eval/semantic_scoring.py:~99-110`) and written to the results row. No decision package imports `dream.eval` (checked by the isolation test), so it cannot reach an agent decision.

## 5. Isaac path specifically

What the Qwen/Isaac evaluation gives the agent that a real robot would not have:

- **Odometry from the simulator** (`isaac_g1.py:10,283,438`): true pose increments plus noise, no visual-inertial or leg odometry. Same as MuJoCo.
- **A closed detector vocabulary with the targets named in it** (`isaac_semantic.py:43-48`; prompt `vlm_detect.py:27-32`). The real Qwen is open-vocabulary and here is told which 14 classes to report. A real robot asked for something outside the list would not have a detector for it.
- **A benign scene set.** Four NVIDIA kitchens, each a single room. Room inference, frontier choice and the "which room" belief contribute little in a one-room scene; the benefit of the semantic prior (the point of the work) is not tested in Isaac at all. The semantic planner uses the MuJoCo-frozen weights unchanged (`FROZEN_WEIGHTS`).
- **Tasks that make refusal the right answer.** The refrigerator is absent (404 assets), the kettle and "far end of the room" are unsupported. A robot that never claims anything scores 0 false successes on these. The only present-target search (the sink) was missed in `g_shape` and not run in two kitchens (README lines 449-475). So the 0/9 false successes cannot be read as evidence of competence, and the README says "no rate is claimed". The cabinet inspection was verified in 1 kitchen.
- **Physics frozen during inference** (README Limitations): the world waits for Qwen. Detection runs only while standing (`detect_when="stationary"`, `isaac_semantic.py:147`).
- **Scoring ground truth from USD labels** (`isaac_semantic.py:true_instances`): oven maps to stove, sink prims are merged by touching boxes with yaw 0 and axis-aligned boxes. The scorer is lenient with a claim tolerance of 0.75 m from a footprint (`semantic_scoring.py:CLAIM_TOLERANCE`), which can accept a claim on a neighbouring object in a cluttered counter run.
